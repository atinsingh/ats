# Observability plan

The plan that every Jobocate service follows for logs, metrics,
traces, dashboards, SLOs, and alerting. This document is
implementation-ready: counters/timers named below already exist in
code where the table marks them "Implemented", and the rest are the
gaps engineering must close before GA.

## 1. Principles

- **Three pillars, one correlation id.** Every log, metric, and span
  carries `correlation_id` (and where applicable `request_id`,
  `tenant_id`, `user_id`) so a single `correlation_id` query in
  Loki/CloudWatch can rebuild the entire request fan-out across HTTP,
  Kafka, and worker boundaries.
- **Multi-tenant by construction.** `tenant_id` is a structured field
  on every log line; it is **not** a Prometheus label (cardinality
  blow-up). Per-tenant numbers live in the analytics warehouse, not
  in Prometheus.
- **Operational vs audit logging is separate.** Audit lives in the
  `audit_events` table (queryable, immutable, exportable).
  Operational logs are sampled and may rotate aggressively.
- **SLOs drive alerts, alerts drive runbooks.** Every SLO has a
  numeric burn-rate alert and a runbook link.

## 2. Logging standards

### 2.1 Format

JSON, one line per event. Required keys:

| Key | Source |
|---|---|
| `ts` | RFC3339Nano UTC |
| `level` | `DEBUG` / `INFO` / `WARN` / `ERROR` |
| `service` | e.g. `application-service`, `search-gateway`, `resume-parser-worker` |
| `env` | `local` / `dev` / `stg` / `prod` |
| `request_id` | Generated by `RequestLoggingFilter` (Java) or equivalent middleware |
| `correlation_id` | Inbound `X-Correlation-Id`; falls back to `request_id` |
| `tenant_id` | From `TenantContext` (HTTP) or event payload (Kafka) — omit if not yet known |
| `user_id` | From `UserContext` — omit if anonymous |
| `logger` | Logger name (`com.jobocate.application.api.ApplicationController`) |
| `msg` | Human-readable message |
| Optional structured fields | `event.id`, `event.type`, `topic`, `partition`, `offset`, `entity`, `duration_ms`, `outcome` |

### 2.2 Implementation

| Surface | How fields land in logs |
|---|---|
| Java services | SLF4J + Logback, MDC populated by `RequestLoggingFilter` (`platform-starter`). Pattern includes `[%X{requestId} %X{correlationId} %X{tenantId} %X{userId}]`. |
| Go `search-gateway` | `slog` JSON handler; middleware copies `X-Request-Id`, `X-Correlation-Id`, `X-Jobocate-Tenant-Id` into the request `slog.Logger` and propagates via context. |
| Python workers | `logging` + `python-json-logger`; consumer copies `tenant_id`, `correlation_id` from event payload before any per-event logging. |
| Next.js apps | Server-side: structured logger that mirrors the Java conventions. Browser-side: console errors are tagged with `correlation_id` from response headers and forwarded to Sentry. |

### 2.3 Sensitive data rules

- **Never** log raw email, phone, full name, resume body, or AI
  prompt/response content at INFO. DEBUG is allowed in non-prod only.
- PII goes through the masking helpers in
  `docs/08-security/security-baseline.md` §11.
- File contents (resumes, cover letters) are never logged. Log the
  S3 key and the size.
- Auth tokens, internal bearer tokens, and Idempotency-Keys are masked
  to first 6 chars + `…`.

### 2.4 Log levels

| Level | When |
|---|---|
| ERROR | Unexpected failure that an operator must investigate (broken invariant, DB unreachable, OpenSearch 5xx, Kafka send failure after retries). |
| WARN | Recoverable failure (retryable Kafka send, soft-rate-limited notification, parser fallback, idempotent duplicate). |
| INFO | Lifecycle events (request start/end, accepted Kafka message, state transition). |
| DEBUG | Diagnostic detail; off in prod. |
| TRACE | Reserved for local debugging only. |

## 3. Correlation IDs

- Inbound HTTP: `X-Request-Id` (echoed back), `X-Correlation-Id`
  (preserved, generated if absent — falls back to `request_id`).
- Outbound HTTP between services: both headers must be propagated.
  The Java `WebClient`/`RestClient` interceptor (planned) reads from
  MDC and adds the headers; `search-gateway` does the same with its
  Go middleware.
- Kafka: producers stamp `correlation_id` and `tenant_id` into the
  message **payload** (not headers) so consumers see them even when
  re-published into DLQ. Consumers populate MDC from the payload
  before processing.
- Workers → callback: workers POST back to `/internal/v1/...` with
  `X-Correlation-Id` mirrored from the originating event.

## 4. Tracing (OpenTelemetry)

- Java services use the OpenTelemetry Java agent (auto-instrumented
  for Spring MVC, JDBC, Kafka clients). Spans include
  `tenant.id` and `user.id` attributes (set from MDC by a custom
  `SpanProcessor`).
- Go `search-gateway` uses `go.opentelemetry.io/otel` instrumentation
  on `chi` and the OpenSearch client.
- Python workers wrap the consumer loop with a manual span per event.
- All services export OTLP/gRPC to a collector. Sampling defaults to
  10% with always-on for `ERROR` traces and a per-tenant sample
  override (post-MVP) when a tenant opens a support ticket.

### 4.1 Span attributes

| Attribute | Source |
|---|---|
| `service.name` | Resource detector |
| `tenant.id` | MDC / context |
| `user.id` | MDC / context |
| `messaging.kafka.topic` | Auto |
| `messaging.kafka.partition` / `.offset` | Auto |
| `messaging.kafka.consumer.group` | Auto |
| `db.statement` | JDBC instrumentation, sanitized |
| `http.route` | Auto |

## 6. SLOs

### 6.1 Service-level objectives (rolling 30 days)

| Capability | SLI | Target | Source |
|---|---|---|---|
| Public job search | P95 of `search_gateway_request_duration_seconds{route="/v1/search/jobs"}` | < **300 ms** | Go gateway histogram |
| Job autocomplete | P95 same metric, route `/v1/search/jobs/autocomplete` | < **150 ms** | Go gateway histogram |
| Application submission success | `application.submitted` ÷ (submitted + failed) at the controller | ≥ **99.5%** | Java micrometer + access log |
| Application submission latency | P95 `http_server_requests_seconds{uri=/api/v1/applications,method=POST}` | < **500 ms** | Spring Boot Actuator |
| Resume parsing latency | Time from `resume.uploaded` Kafka publish → `resume.parsed` Kafka publish, P95 | < **30 s** | event timestamps |
| Notification dispatch latency | Time from event acceptance → SENT, P95 | < **60 s** | `notification.dispatched` timer (planned) |
| Search indexing freshness | Time from `job.published` Kafka publish → searchable in OpenSearch, P95 | < **10 s** | event ts vs `_doc.indexed_at` |
| API availability (per service) | `1 - 5xx ÷ total` excluding `/actuator/**` | ≥ **99.9%** | Spring Boot Actuator |
| Kafka consumer freshness | `kafka_consumergroup_lag` per critical group | < **1000 messages** | Kafka exporter |

### 6.2 Error budget policy

- Each SLO compiles into a 30-day budget. Breaching the budget
  freezes feature deploys for the affected service until the burn
  rate returns to baseline (plus one full day of healthy operation).
- Multi-window multi-burn-rate alerts:
  - **Fast burn**: 14.4× the budget over 1h → page primary on-call.
  - **Slow burn**: 6× the budget over 6h → page primary on-call.
  - **Trend**: 1× the budget over 3 days → ticket; no page.

## 7. Alerting

| Alert | Severity | Trigger | Runbook |
|---|---|---|---|
| Search latency burn | P1 | Search SLO fast-burn | `runbooks/search-latency.md` |
| Application submission failures | P1 | Submission SLO fast-burn or any 30-min burst > 5% errors | `runbooks/application-submission.md` |
| Resume parsing stalled | P2 | `resume.uploaded → resume.parsed` lag P95 > 5 min for 15 min | `runbooks/resume-parsing.md` |
| Kafka consumer lag (critical group) | P1 | `kafka_consumergroup_lag` > 1000 for 10 min | `runbooks/kafka-lag.md` |
| Notification failure rate | P2 | `notification.failed ÷ notification.dispatched` > 1% over 30 min | `runbooks/notification-dispatch.md` |
| OpenSearch cluster health | P1 | Cluster status `red` for 5 min | `runbooks/opensearch.md` |
| DB connection saturation | P2 | HikariCP active connections > 80% capacity for 10 min | `runbooks/postgres.md` |
| Outbox backlog | P2 | `event_outbox` rows where `status='PENDING' AND created_at < now() - interval '5 minutes'` count > 100 | `runbooks/outbox.md` |
| Spring Boot HTTP 5xx | P2 | `http_server_requests_seconds_count{status=~"5.."}` > 1% per 30 min | per-service runbook |

## 9. Audit vs operational logging

| Property | Operational logs | Audit log |
|---|---|---|
| Storage | Loki / CloudWatch / Stackdriver (depending on env) | `audit_events` table (Postgres) |
| Retention | 30 days (prod), 7 days (stg/dev) | 7 years (prod), per compliance |
| Mutability | Immutable in storage; rotated | Application-write-only; `INSERT` privilege only |
| PII | Masked / minimal | Pseudonymized actor ID; sensitive payloads stored as references |
| Sampling | 100% for ERROR; 10% for INFO/DEBUG in prod | Never sampled |
| Format | JSON line | Structured row with `id`, `tenant_id`, `actor_user_id`, `action`, `entity_type`, `entity_id`, `payload`, `created_at` |
| Query path | Loki / Cloud logs UI | Compliance UI + warehouse export |

`audit_events` rows are written transactionally by the same service
that performs the action, in the same DB transaction. Cross-service
audit (e.g. "this Kafka event was processed") is captured in
operational logs, not audit.

## 10. Health endpoints

- Java: Spring Boot Actuator `/actuator/health` (liveness +
  readiness), `/actuator/info`, `/actuator/prometheus`. `/actuator/**`
  bypasses authentication (covered in `security-baseline.md`).
- Go: `/healthz` (liveness), `/readyz` (checks OpenSearch
  reachability + a no-op search), `/metrics`.
- Python: lightweight HTTP `/healthz` exposing `{ ok: true }` for
  Kubernetes probes.

## 11. Runbooks

Each runbook lives under `docs/15-observability/runbooks/` (planned)
and follows the structure:

```
# Runbook: <symptom>

## Page severity
## Likely impact
## First-5-minutes checklist
## Common causes
## Detailed steps
## Escalation
## Post-incident
```

Initial set: `search-latency.md`, `application-submission.md`,
`resume-parsing.md`, `kafka-lag.md`, `notification-dispatch.md`,
`opensearch.md`, `postgres.md`, `outbox.md`.

## 12. Implementation checklist (per service)

- [ ] Logback / `slog` / `python-json-logger` outputs JSON with the
      required keys.
- [ ] Inbound `X-Request-Id` and `X-Correlation-Id` are honored;
      generated when absent; echoed in response.
- [ ] All outbound HTTP/Kafka calls propagate `X-Correlation-Id`.
- [ ] At least the standard counters / timers in §5 are registered.
- [ ] OTLP exporter configured to point at the env's collector.
- [ ] `/healthz` and `/readyz` (or Actuator equivalent) return
      meaningful checks (DB, Kafka, OpenSearch where applicable).
- [ ] An entry in the dashboard catalog (§8).
- [ ] At least one alert + runbook for the service's most-critical
      failure mode.
